# UnderHood CMS для Render

Исходный интерфейс UnderHood сохранён. Сервер перенесён с Cloudflare R2 и платформенной авторизации на Flask + SQLite с обычным входом email/пароль.

## Развёртывание

- Render Web Service, Python, план `0.5c-512mb` ($7/месяц по прайсу 26.10.2026).
- Build: `pip install -r cms/requirements.txt`.
- Start: `gunicorn --no-control-socket --workers 1 --threads 2 --timeout 90 --bind 0.0.0.0:$PORT 'cms.app:create_app()'`.
- Постоянный диск 1 GB ($0,25/месяц), mount path `/var/data`.
- `DATA_DIR=/var/data`, `REQUIRE_PERSISTENT_DISK=1`, `COOKIE_SECURE=1`.
- `CMS_ORIGIN` — точный HTTPS origin сервера CMS без завершающего `/`.
- `ADMIN_EMAIL` — email владельца. `ADMIN_PASSWORD_HASH` — scrypt-хеш начального пароля; секрет задаётся в Environment, в Git не хранится.
- `PUBLIC_SITE_URL=https://underhood-detailing.onrender.com`.
- Health check `/api/health`.

Конфигурация также описана в корневом `render.yaml`. Для уже созданного вручную сервиса используйте Dashboard как источник настроек; не создавайте второй сервис через Blueprint.

Без смонтированного постоянного диска запуск прекращается. Это защищает от сохранения контента на временную файловую систему Render. Диск требуется именно в `/var/data`, а не во вложенной папке.

При первом запуске создаётся единственный владелец и исходный контент. При первом входе владелец обязан сменить временный пароль. Изменение начальных env-параметров впоследствии не сбрасывает сохранённый пароль. Сброс через Shell: `python -m cms.manage reset-password` (пароль вводится без отображения).

## Данные и резервные копии

SQLite, сессии и WebP-фотографии находятся только на постоянном диске. Запись контента, резервная копия и проверка ревизии выполняются одной транзакцией. Хранятся последние 30 версий. Фото из старых версий не удаляются автоматически, чтобы восстановление сохраняло работоспособность.

Лимит — 50 работ и 30 FAQ. Фотографии проверяются сервером, уменьшаются до 1920 px по длинной стороне и повторно кодируются в WebP до 1,2 МБ. Водяной знак применяется один раз сервером. На фото выделено до 600 МБ; при исчерпании лимита новые загрузки отклоняются, существующие данные сохраняются.

Кнопка «Скачать архив с фото» выгружает контент, историю и используемые ими фото. Пароли и сессии в архив не включаются. Архив можно хранить вне Render. Восстановление полного архива выполняется при остановленном веб-процессе: `python -m cms.manage restore-archive /path/to/underhood-backup.zip --replace`. Перед импортом создаётся согласованная копия существующей SQLite-базы. Резервные версии внутри админки восстанавливаются без остановки сервиса.

Перезапуск и деплой сохраняют данные на диске. Render временно останавливает сервис с диском при обновлении; публичный статический сайт продолжает показывать локальные тексты, если CMS недоступен.

## Публичный сайт

Админка доступна на `/admin`, API — `/api/content`, фотографии — `/api/media/<uuid>.webp`. Публичный сайт переключается на новый origin в `content.js` только после проверки сервера. До этого он продолжает использовать прежний CMS. `build.sh` публикует только проверенный список файлов в `dist`; `cms/`, тесты, SQLite, env-файлы и резервные копии туда не входят.

Исходники прежнего CMS сохранены отдельно. Прежняя платформа не дала авторизованного доступа к API управления и истории (403), поэтому старые приватные резервные копии не объявляются перенесёнными. Публичный старый API возвращал `content:null`, исходный контент совпадал с репозиторием. Старый CMS не изменяется и не отключается.

## Проверки

`python -m pytest -q tests/test_cms.py` проверяет авторизацию/CSRF, обязательную смену пароля, завершение сессий, защиту входа от перебора, два одновременных сохранения, отказ резервной записи, лимиты, изображения, экспорт и сохранность после повторного запуска приложения. Отдельная браузерная проверка проверяет вход, редактор после нескольких сохранений, загрузку фото, конфликт двух вкладок, скачивание черновика/архива, восстановление, выход и мобильный интерфейс.
